# 포트폴리오 구조 개편 — 오픈소스 기여 중심 설계

작성: 2026-10-06 · 상태: 사용자 승인

## 1. 목적

- AI 덕분에 단일 페이지나 기능을 만드는 일은 쉬워졌습니다. 그래서 기업은 다른 사람이 검토하고 병합한 오픈소스 기여처럼 **검증된 개발 능력**을 더 중요하게 봅니다. 사이트의 무게를 오픈소스 기여로 옮깁니다.
- 홈 구조를 **오픈소스**와 **개인 프로젝트** 두 장으로 나눕니다.
- 상태가 바뀌는 값(병합·리뷰·닫힘, 병합 PR 수, PyPI 릴리스)은 **매일 자동으로 갱신**해서, 사이트 내용이 사실과 어긋나지 않게 합니다.

## 2. 결정

| 항목 | 결정 |
|---|---|
| 오픈소스의 범위 | 외부 프로젝트에 낸 이슈·PR과, 내가 공개로 운영하는 오픈소스를 모두 넣는다. 외부 프로젝트는 PyTorch·vLLM·SGLang·ComfyUI다. 공개 운영 오픈소스는 Entail, torch.compile 퍼저, 글, inversa-bench, asahi다. |
| 개인 프로젝트 | 바른오더, 맛집큐브, nogada RPG(가로 데크)와 카드·한 줄 목록. |
| 최신화 | GitHub Actions가 매일 06:00(KST)에 GitHub와 PyPI에서 상태를 읽는다. 바뀐 것이 있으면 `src/data/contributions.json`을 커밋하고, 이 커밋으로 Vercel이 배포한다. 실패하면 커밋하지 않는다. |
| 병합 판정 | `merged`가 참이면 병합이다. PyTorch처럼 봇으로 병합하는 저장소는 닫혔고 `Merged` 라벨이 있으면 병합으로 본다. |
| 표현 | "PyTorch 기여자 · 병합 N건". 칭호에는 반드시 건수를 붙이고, N은 데이터에서 계산한다. |

## 3. 홈 구성

1. 히어로: 오라클 장면은 그대로다. 소개 문장의 PyTorch 부분은 데이터에서 계산한다.
2. 핵심 성과(4개):
   - PyTorch 기여자(병합 N건)
   - 외부 오픈소스(N개 프로젝트에 이슈·PR)
   - 글 언어 자체 호스팅(194/194)
   - asahi(main 병합 PR N건)

   계산할 수 있는 숫자는 모두 데이터에서 계산한다.
3. **1장 오픈소스** (`#oss`)
   - 장 간지: 「1장 · 오픈소스 — 검증받은 기여와 직접 운영하는 오픈소스」
   - **외부 프로젝트 기여 보드**(새 장면, `data-scene="contrib"`)
     - 맨 위 요약: 병합, 리뷰 중, 이슈, 프로젝트 수. 숫자가 세어 올라간다.
     - 저장소별 묶음: 저장소 링크, 건수, 찾은 도구(퍼저·Entail) 링크.
     - 항목: 종류(이슈·PR), 상태 칩, 제목 링크 ↗, 다른 개발자의 관련 수정 PR과 그 상태.
     - 상태 칩: 병합, 승인, 리뷰 중, 변경 요청, 닫힘, 열림, 해결. 글자로도 표시해서 색에만 기대지 않는다.
     - 맨 아래: "매일 자동 확인 · 마지막 변경 YYYY-MM-DD".
     - 움직임: 묶음 단위로 `playOnEnter`. 행은 투명도와 위치로 등장하고, 병합 칩은 도장처럼 찍힌다(되튐 곡선). 움직임 줄임에서는 최종 상태만 보인다.
   - **직접 운영하는 오픈소스**: 소제목 아래에 기존 대표작 장면 5개(Entail, 퍼저, 글, inversa-bench, asahi)를 둔다. 계획 2의 시연은 나중에 이 자리에 들어간다.
4. **2장 개인 프로젝트** (`#personal`)
   - 장 간지: 「2장 · 개인 프로젝트 — 직접 만든 제품과 실험」
   - 가로 데크 3장(바른오더, 맛집큐브, nogada)
   - 그 뒤 `#more`에 카드와 한 줄 목록
5. 경력, 일하는 방식, 기술 스택, 마무리는 그대로 둔다.
6. 상단 목차: 01 오픈소스(`/#oss`) · 02 개인 프로젝트(`/#personal`) · 03 경력 · 04 연락처

## 4. 데이터

`src/data/contributions.json` 하나에 두 종류의 필드를 둔다.

- **사람이 관리하는 필드**: `project`(찾은 도구, 대표작 id 또는 `null`), `note`, `related`(다른 개발자의 수정 PR 목록), 최상위 `ignore`(목록에서 뺄 항목).
- **스크립트가 갱신하는 필드**: `title`, `state`(`open`·`merged`·`closed`), `stateReason`(이슈), `review`(`approved`·`changes_requested`·`review_required`·`null`), `labels`, `createdAt`, `closedAt`, `mergedAt`, `related[*]`의 상태와 작성자.

그 밖의 데이터:

- 최상위 `asOf`: 마지막으로 바뀐 시각.
- `own`: 내 프로젝트의 수치. `asahi.mergedPrs`(main 병합 PR 수)와 `entail.pypiReleases`·`entail.pypiLatest`.

새로 올린 외부 이슈·PR은 작성자 검색(`author:wwoosshh -user:wwoosshh -org:semicollon-club`)으로 자동 추가한다. 이때 `project`는 `null`이다.

보여 주는 숫자는 모두 `src/lib/contribution-stats.ts`에서 계산한다. 퍼저·Entail·asahi의 상태성 수치는 MDX에 직접 적지 않고 `src/lib/live-metrics.ts`가 만든다. 이 수치는 홈, 상세 페이지, 인쇄에 모두 쓰인다.

## 7. 테스트

- **단위 테스트**
  - 병합 판정(`merged`, `Merged` 라벨), 정규화, 사람이 관리하는 필드 보존, 새 항목 추가, `ignore` 처리
  - 통계 계산
  - 스키마 검사(이슈는 `merged`가 될 수 없음, URL 형식)
- **e2e**
  - 홈 장 순서와 목차 링크
  - 기여 보드의 저장소별 묶음, 상태 칩 글자, 링크 ↗·rel
  - 움직임 줄임·JS 없음에서도 내용이 모두 보인다
  - 데크 3장
- **기존 규칙 유지**: 장면 규칙(`playOnEnter`, `autoAlpha` 금지), 디자인 규칙, 대비, 모든 경로에서 숨은 요소 없음.
